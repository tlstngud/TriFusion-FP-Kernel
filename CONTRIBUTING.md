# Contributing

Use a virtual environment. Install `.[dev]` for packaging/CPU tests and `.[l4]`
with the documented CUDA PyTorch wheel when working on GPU code.

```bash
ruff check .
ruff format --check .
python -m pytest -q
python -m build
python -m twine check dist/*
```

For numerical kernel changes, run the recurrence tests on L4 with the pinned
framework stack. Report shapes, warmup, repetitions, synchronization, peak memory,
and both latency and output differences. Clearly separate model-forward timings
from decoding/loading/compilation. Keep the portable reference independent of
the optimized implementation.

Preserve upstream license notices and update `THIRD_PARTY_NOTICES.md` when
changing derived code. Keep model weights, audio, machine credentials, local
paths, and per-record inference outputs out of commits. GPU CI is not currently
available; CPU checks alone are not GPU validation.

## Publishing a release

The PyPI project is `trifusion-fp-kernel`. Trusted Publishing is bound to
`tlstngud/TriFusion-FP-Kernel`, `.github/workflows/release.yml`, and the GitHub
environment `pypi`. Only the upload job has `id-token: write`; no PyPI API token
or password is required. Deployment is allowed from `main` and `v*` tags.

1. Update the package version, tests, and changelog. Run the checks above, then
   build into a clean `dist/` directory. Check the distributions for unintended
   files before publishing.
2. Create a draft GitHub release with a matching `vVERSION` tag. Upload its
   wheel, sdist, and `SHA256SUMS` (generated by `sha256sum *.whl *.tar.gz` from
   `dist/`). Publish the release only after all three assets are present.
3. Publishing the GitHub release triggers `release.yml`. It verifies both
   hashes, package names, and versions, checks metadata and the installed CLI,
   then uploads the same distribution bytes to PyPI with OIDC attestations.

For an already published GitHub release, including the initial `v0.1.0`, run:

```bash
gh workflow run release.yml --ref main -f tag=v0.1.0
```

PyPI versions are immutable. Do not rebuild or replace the files of a version
already on PyPI; publish a new version instead. The workflow does not silently
skip existing files.
